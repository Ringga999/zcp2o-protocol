SPEC-01 · Explorer Hash Lib

Goal: complete the Explorer with hash transparency & verification, so anyone can audit chain integrity from the browser.

Features

  • Chain Integrity card — new endpoint GET /chain/valid returning bunker.is_chain_valid(); Explorer shows ✅ Chain intact or a warning.
  • Block detail drawer — click a block → full hash, previous hash, transaction list.
  • Per-block verify — new endpoint GET /block/{i}/verify → server recomputes the block hash → true/false.

Design rule

Canonical hashing stays server-side only. The browser must NOT recompute hashes (serialization must be byte-identical; keep one source of truth).

SPEC-02 · Circle Launcher (Proof-of-Play game)

Goal: a light, addictive PoP game (simpler than Alpha Drop) that turns players into contributing nodes/validators.

Core loop

  • Player = blue circle; enemies = red circles.
  • World = a "block server" of 10,000 px, max 100 players per block server.
  • World 1 — entry: solve ZCP2O captcha. Prize: gold tokens. Session 5–15 min (random, anti-bot-farm).
  • World 2 — entry: captcha + spend 100 gold/session. Prize: gold, XP, and $ZPRO. Session 5–15 min (random).
  • Currency spawn is backed by on-chain activity: coins appear because the blockchain is active; a player who claims is a node/validator contributing to the chain.

Objectives

  • Become a validator under Proof-of-Play.
  • World 1 → earn a silver ticket. World 2 → earn $ZPRO.

Features

  • Main menu · World 1 · World 2
  • In-game wallet (transfer / receive)
  • Leaderboards: XP, earliest players, monthly / yearly / all-time (framed as activity recognition, not dark-pattern)

Block-server sharding & fill policy

  • Full block server (100) → chain auto-generates a new block server.
  • When players leave, the earliest block recruits first.
    Example: A=100, B=100 → A−3, B−2 → new player joins A → A=98, B=98.

Asset & data mapping (on-chain vs off-chain)

Asset / dataLocationReason
$ZPRO rewardon-chain (REWARD/transfer)real value
Silver ticketon-chain (tx_type="TICKET")season proof
Session result + XP deltaon-chain (settlement tx)auditable
Gold tokenoff-chain (game DB)fast, no chain bloat
Positions / enemies / ticksoff-chain (session memory)ephemeral
Leaderboardoff-chain cache + on-chain checkpoint per sessionfast view, auditable root

Validator anchor

Players co-sign block hashes into the existing block.validator_signatures field — a real attestation hook already present in the core (used by fork-resolution). No multi-node rebuild needed for MVP.

Anti-bot layers

  • Captcha gate per session · random session length · cooldown
  • Motor human-ness score from the captcha telemetry seeds player trust (too-perfect bots get a smaller reward pool)

Transport reality

Free-tier hosting has no WebSocket → use tick-based polling (2–3 s), server-authoritative. The block-server sharding also spreads load, which suits free-tier limits.

Phasing

  • G0 — this spec + offline canvas prototype (game feel)
  • G1 — captcha gate + tick sessions + $ZPRO rewards via existing plumbing + leaderboard checkpoints
  • G2 — multi block-server + gold economy + validator_signatures attestation

SPEC-03 · Human-Proof Stats & widget hygiene

Finding

The wallet captcha and the standalone zcp2o-captcha demo use the same engine (embed.js + zcp2o-hp*.js). The difference is only whether the token is submitted to the Bunker:

WhereToken submitted?On-chain?
Wallet (claim / register)yes → /claim, /identity/registeryes (REWARD tx / pioneer)
Standalone demono (token stays local)no — by design

Raw solves are intentionally NOT on-chain (privacy-first: 0 bytes exfiltrated). Only submitted events (claim, transfer, register) become on-chain records.

Proposal

  • New aggregate endpoint GET /stats → count of verified proofs (no identity).
  • Explorer card: "Human proofs verified: N" — visibility without surveillance.

Widget bug to fix

Console shows Uncaught SyntaxError: Identifier 'vmB' has already been declared across zcp2o-hp*.js → challenge scripts share global scope. Fix: wrap each challenge file in an IIFE.

SPEC-04 · Captcha-as-Validator Infrastructure (Mass Adoption)

Goal: enable any developer to embed ZCP2O captcha as human verification, where every solve contributes to chain consensus as validator attestation.

Architecture layers

  • Registration — solve captcha → register as validator → get validator_id on-chain (0 cost)
  • Contribution — each solve tracked off-chain (Bunker DB) + checkpoint on-chain per 100 solves/day (scalability)
  • Validator selection — high trust-score validators co-sign blocks via block.validator_signatures
  • Micro-rewards — reward per 10 validations (incentive alignment)
  • Domain stats — endpoint /stats/{domain} for each developer
  • Explorer visibility — per-domain contribution card: "X solves → Y validated blocks"

Challenges & solutions

ChallengeSolution
Scalability (1000s solves/day)Batch validation + off-chain tracking
Sybil resistanceRate-limit + cooldown + origin-binding + human-ness telemetry
Incentive alignmentMicro-rewards per 10 validations
ObservabilityDomain stats endpoint + Explorer card

Principle anchor

This spec realizes the core ZCP2O principle: "captcha = validator" — not metaphor, but technical attestation on-chain.

SPEC-05 · Runtime State Sovereignty

Goal: ensure node runtime state (SQLite database, logs) is NEVER tracked by Git, so restarts/pulls don't wipe chain history.

Problem discovered

  • zcp2o_node.db was tracked → git pull --hard overwrote live database → chain reset to genesis
  • Logs were tracked → merge conflicts on every restart

Solution

  • Untrack *.db and logs/ via git rm --cached
  • Add to .gitignore: *.db and implementations/zcp2o-node/logs/
  • Backup/restore workflow during Git sync

Status

✅ LIVE — database and logs now sovereign, immune to Git operations.
